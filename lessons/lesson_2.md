# Lesson 2: RSpec and Testing Models

## Concept 2.1: Test-Driven Confidence in Model Logic

### Explain

RSpec is a testing framework for Ruby that emphasizes readability and developer experience. Unlike Minitest, which blends test structure with Ruby syntax, RSpec uses a domain-specific language that reads like specifications: "a bank account should deposit money" or "a profile should return a full name."

In Rails, models are the backbone of your application. They contain business logic, validations, and relationships. Testing models in isolation gives you fast feedback and protects against regressions when you refactor. The patterns you learn here — `let`, `before`, `subject`, `expect` — carry over to every other type of spec you'll write.

RSpec introduces a few key concepts:
- **`describe` and `context`** group related examples
- **`it`** defines a single example/test
- **`expect`** is the assertion mechanism
- **`let`** defines memoized helper methods
- **`subject`** defines the object under test
- **`before`** runs setup code before examples

### Setup

**Step 1: Add RSpec to the project**

Edit your `Gemfile` and add:

```ruby
group :development, :test do
  gem "rspec-rails", "~> 8.0"
end
```

Then run:

```bash
bundle install
bin/rails generate rspec:install
```

This creates:
- `.rspec` — configuration flags
- `spec/` — the test directory
- `spec/rails_helper.rb` — Rails-specific test configuration
- `spec/spec_helper.rb` — core RSpec configuration

**Step 2: Verify the setup**

```bash
bin/rails spec
```

You should see a message about no examples found, or a passing placeholder spec. If you see errors, check that `rails_helper.rb` loads correctly.

> Note: `bin/rspec` is not generated by default. Use `bin/rails spec` or `bundle exec rspec` to run specs.

**Step 3: Configure RSpec**

Open `.rspec` and make sure it includes helpful flags:

```bash
--format documentation
--color
```

This gives readable output when you run specs.

### Practice

**Task 1: Test `BankAccount` deposit and withdraw**

Goal: Write specs that verify `BankAccount` enforces encapsulation and handles edge cases.

Requirements:
- A `BankAccount` starts with a `nil` balance
- `deposit(100)` increases the balance
- `withdraw(30)` decreases the balance after a deposit
- `deposit(-5)` raises `ArgumentError`
- `withdraw(-10)` raises `ArgumentError`
- `withdraw(1000)` on an account with balance 50 raises `InsufficientFunds`

Hints:
- Use `let(:account) { BankAccount.create! }` to create a test subject
- Use `expect { account.deposit(-5) }.to raise_error(ArgumentError)` for error testing
- Use `expect(account.balance).to eq(expected_value)` for value testing
- `BigDecimal` values in the database display as `0.1e3` in the console, but comparisons still work — use `to_d` or `eq` with a `BigDecimal` if needed
- Test one behavior per `it` block. Name examples descriptively: `"deposits a positive amount"` not `"works"`

Write specs in `spec/models/bank_account_spec.rb`.

**Task 2: Test the `Profile` value object**

Goal: Verify `Profile` behavior in isolation, without hitting the database.

Requirements:
- `Profile.new(first_name: "Ada", last_name: "Lovelace", address: "London")` creates a valid profile
- `profile.full_name` returns `"Ada Lovelace"`
- Changing the original attributes after creation does not affect the profile (immutability)
- `first_name`, `last_name`, and `address` are readable

Hints:
- Use a plain `let(:profile) { Profile.new(...) }` — no `BankAccount.create!` needed
- Test immutability by creating a profile, then checking that its attributes don't change
- `Profile` is a value object, so two profiles with the same data should be considered equal in your tests
- You can test `attr_reader` behavior directly: `expect(profile.first_name).to eq("Ada")`

Write specs in `spec/models/profile_spec.rb`.

**Task 3: Test polymorphic `Notifiable` behavior**

Goal: Verify that `Article` and `Video` both respond to `notify(message)` with different output.

Requirements:
- `Article#notify("new comment")` returns `"Article update: new comment"`
- `Video#notify("new comment")` returns `"Video alert: new comment"`
- Calling `notify` on a model that includes `Notifiable` but doesn't override it raises `NotImplementedError`

Hints:
- Create instances with `let(:article) { Article.create!(title: "Test") }` and `let(:video) { Video.create!(title: "Test") }`
- Use `expect(article.notify("x")).to eq("Article update: x")`
- Test the base module behavior by creating a temporary class that includes `Notifiable` without overriding `notify`, or test it through a model that forgets to implement it
- This task is about polymorphism: same interface, different behavior — your specs should demonstrate that

Write specs in `spec/models/notifiable_spec.rb` or `spec/models/article_spec.rb` and `spec/models/video_spec.rb`.
